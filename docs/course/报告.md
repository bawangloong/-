# 车牌识别系统课程报告

小组用 Python 完成车牌检测、矫正、颜色判断、字符分割，再与字符库匹配，并由界面把这些步骤串成一次调用。本报告只使用仓库里已经落地的代码、说明，以及 `eval/results/system-evaluation.json` 里那一次冻结运行。A、B、C 各自文档中的合成集或字符集分数不写入下面的课程测试表。

## 1. 分工

代码分别在 `received/a/`、`received/b/`、`received/c/`、`received/d/`，系统入口在 https://github.com/bawangloong/plate-recognition-submit 。E 做的是数据、评测和把这些材料收成报告、幻灯片与讲稿。

| 角色 | 已经落地的工作 | 位置 |
| --- | --- | --- |
| A | 检测是否有车牌，在原图上给出框和四角点，并输出摆正的车牌图。`color_hint` 只是底色线索。 | `received/a/`，方法见 `received/a/docs/A模块报告初稿.md` |
| B | 对一块已经裁好的车牌判断颜色，并切出从左到右的字符图。 | `received/b/`，方法见 `received/b/report_B.md` |
| C | 把有序字符图与字符库比对，拼出号码。不检测整张街景。 | `received/c/`，方法见 `received/c/方法讲解.md` |
| D | 把检测、矫正、颜色、分割、识别串成 `PlatePipeline`，并做 Tkinter 界面、异常码和打包说明。 | `received/d/`，根目录调用在提交仓库的 `pipeline.py` |
| E | 四个划分、标注、清单、`evaluate.py`，以及这次课程测试表和本报告。 | `data/`、`eval/`、`docs/course/` |

这次被评测的 `pipeline.run` 来自提交仓库提交 `d7e9d13c6ed0361f9b7cebeefa9d0eb59d3c7ec3`。该克隆的 `vendor/a_plate/` 是空的，检测走 `app/detector.py` 里的内置实现，框上的 `source` 为 `color:*` 或 `gradient`。因此下面的定位数字衡量的是这套内置检测，不是 `received/a/detect_plate.py` 的另一次运行。

## 2. 一次识别怎么走

D 的集成顺序是：

1. 用 Pillow 读图，支持中文路径，并按 EXIF 摆正方向。
2. 检测。优先查找 `vendor/a_plate/`；找不到时用内置检测。没有车牌时 `plates` 为空，`error.code` 为 `no_plate`。
3. 按四角点做透视矫正。矫正失败的候选不会进入后面的识别。
4. B 的颜色：在摆正图上统计 HSV，得到 `blue`、`yellow`、`green`、`white`、`black` 或 `unknown`。
5. B 的分割：高度归一到 140 像素后投影切字，输出 40×20、白笔画黑背景的字符图，以及 `count` 和 `status`。`count_abnormal` 与 `no_char` 仍保留实际切出的个数。
6. C 的匹配：7 或 8 个字符用 `standard` 布局，其它长度用 `unrestricted`。返回整牌字符串和每个字的相似度。
7. D 按置信度丢掉一部分候选。输出里若出现「识别置信度低，按误检丢弃」，这块牌不会出现在最终 `plates` 里。

评测在计分前把提交仓库的字段收成指标字段：`bbox` 收成 `{x,y,w,h}`，`color.color` 收成颜色字符串，`segmentation.count` 收成 `char_count`，`text` 收成 `number`。

## 3. 各模块的方法

方法原文在各角色自己的文档里。这里只保留和接口、失败现象有关的部分。

### 3.1 检测与矫正（A，以及本次实际用到的内置检测）

A 的方案是 OpenCV 传统方法，不训练网络。颜色通道在 HSV 里分别取蓝、黄、绿、白掩码；边缘通道用竖直边缘把字符区连成块。候选要经过长宽比、尺寸、倾角、字符投影峰和评分，再用 NMS 去掉重叠框。矫正把四角点透视到正向车牌，并保留 3×3 的 `transform`。无车牌时返回空列表。异常文件抛 `PlateIOError`。

D 在 A 的文件还没放进 `vendor/a_plate/` 时，使用同一思路的内置后端：HSV 底色、梯度纹理和透视矫正。本次课程运行走的是这一条。

### 3.2 颜色与字符分割（B）

颜色不去训练分类器。去掉四周一圈边缘后，在饱和且不太暗的像素上按色相归入蓝、黄、绿；某一档占比超过 45% 就采用该颜色。饱和像素太少时，再按亮度区分白牌和黑牌，否则为 `unknown`。

分割先把高度缩放到 140 像素，灰度后用 Otsu，并按前景占比自动决定白字还是黑字。投影得到字符列，合并过近的碎块，拆开过宽的粘连，丢掉分隔圆点。普通牌常见 7 个字符，新能源牌常见 8 个。切出的个数不是 7 或 8 时，状态为 `count_abnormal`，个数仍按实际值上报。

D 的集成说明里，分割增加了可选参数 `min_char_width_ratio`。B 自己的默认仍是 0.25；D 调用时传入 0.10，避免窄字符被当成噪点删掉。这是 D 文档里的集成改动。课程表不使用他们附带的 6 张合成牌或 8 张 `samples/`。

### 3.3 字符库匹配（C）

C 收到的是已经排好序的字符图。每张图先统一成白字黑底，再放进 32×32 画布。特征是手写的 HOG（324 维）加上归一化像素（1024 维），合成 1348 维单位向量。相似度是查询向量和样本向量的点积。每一类取最相似的一张样本，再取全库最高的一类作为该字。

类别是 65 个：数字、去掉 I 和 O 的大写字母，以及 31 个省份简称。库里没有学、警、使、领、港、澳、挂。因此警牌末位「警」、使馆牌的「使」、粤澳牌的「澳」不在这 65 类里。C 自己的字符集评估在 `received/c/results/`，那是字符图上的实验，不是本报告的整图测试表。

### 3.4 界面与异常（D）

界面用 Tkinter。左侧显示原图和框，下方可切换多块牌；右侧有号码、颜色、字符切片和二值化过程。识别在工作线程里跑，主线程只刷新界面。

用户能直接看懂的错误码包括：不支持的扩展名 `unsupported_type`、空文件 `empty_file`、损坏图片 `decode_failed`、图片过小 `image_too_small`、没有车牌 `no_plate`、字符库缺失 `library_missing`。单块牌失败时记入警告，并继续处理下一块。

`received/d/` 里的 `车牌识别系统.exe` 约 4.6 KB，只是启动器。完整的 `runtime/` 因为单个 `cv2.pyd` 超过 GitHub 文件大小限制，没有放进本仓库。D 的 `docs/另一台电脑测试记录.md` 写明：开发机上曾用收紧 PATH 的方式打开过界面；第二台物理电脑的复测表仍是空的。本报告不把 exe 说成已在另一台 Windows 电脑上测试通过。E 也没有在本机重开 GUI。

## 4. 数据与划分

正式图像在 `data/raw/`，标注在 `data/annotations/annotations.jsonl`，名单在 `data/splits/manifest.json`。一共 29 张。每条 `source` 写了来源页和许可名称。来源包括维基共享资源上的公开照片，以及 CCPD 官方仓库 `rpnet/demo/` 的 5 张示例。号码是对着图像读的。看不清的牌 `number` 留空。

| 划分 | 张数 | 用途 |
| --- | --- | --- |
| development | 7 | 调试。演示要用图时用这一档，不从终测里抽。 |
| library | 5 | 只给字符库切样本。与两个评测划分没有重复图像。 |
| validation | 8 | 评测。 |
| final_test | 9 | 评测。名单已冻结，这次没有增删。 |

验证集和终测集都包含无牌、多牌、蓝、黄、绿、白、黑、倾斜、模糊和反光。青绿厂内牌和人力车牌归入 green。颜色闭集里没有红色。三块牌的号码为空：验证集里被裁切的货车牌、加州模糊牌，以及终测里被涂糊的摩托车牌。这三块不参与逐字和整牌。

`python3 data/check_dataset.py` 对这 29 张的检查结果是退出码 0：没有完全重复，也没有汉明距离不超过 5 的近似重复。提交仓库 `samples/` 的 8 张合成图没有进入清单。

## 5. 指标怎么算

口径在 `eval/README.md`。这次运行的命令是对冻结清单调用 `pipeline.run`，划分是 validation 和 final_test，IoU 阈值 0.5。

- 车牌是否存在：标注的 `has_plate` 与预测列表是否非空，按图像计。
- 定位：同一张图内 IoU ≥ 0.5 贪心配对。精确率 = TP / (TP+FP)，召回率 = TP / (TP+FN)。
- 颜色、字符数量：只统计已经配上的车牌。
- 逐字和整牌：号码归一化后为空的标注不进入分母。定位命中后的比例只看配上的牌；端到端把没配上的有号码车牌也算进分母，这些字和整牌都算错。
- 运行时间包住每一次 `pipeline.run`，不含读清单和写报告。

`eval/evaluate.py --fixture` 的输出只检查指标算术，不出现在下表。

## 7. 同一次运行里的失败

逐张期望值和实际值在 `eval/results/system-evaluation.md`。模块只在输出字段写明阶段时填写。

配上并读出号码的有五块：

- 验证集多牌图里的黄牌 `ZM1433`，预测 `1A豫`。分割状态是 `count_abnormal`，字数 3，和标注的 6 不一致，记在字符分割。
- 终测黄牌 `陕AA9087`，预测 `A冀渝7`，字数 4，同样是分割个数异常。
- 终测两块大型绿牌 `粤B12345D`、`粤B12345F`，预测 `12345D`、`12345F`，各少了开头两个字，分割个数为 6。
- 终测人力车牌 `西城0414`，预测 `晋冀0414`。字数同为 6，后四位一致，前两个汉字不同。识别状态是 `needs_review`，记在字符识别。颜色仍是 green。

其余有号码的牌没有配上框。其中多张图的 `warnings` 写着候选因置信度低被丢掉，最终 `plates` 为空，存在判断因此算错。两张无牌图（俯视停车场和车公庙空场）各预测出 3 块牌，框的 `source` 来自内置颜色检测。三块空号码牌不进入逐字和整牌；它们的漏检只影响定位和存在判断。

这张表说明：在这 17 张图上，内置检测加上置信度过滤只留下了 5 个命中框；颜色在这 5 个框上都对；整牌字符串没有一块与标注完全相同。端到端整牌 0/16，是因为没配上的 11 块有号码车牌也算错。

## 8. 复现

在本仓库根目录，清单和标注使用默认路径：

```bash
python3 data/check_dataset.py
python3 eval/evaluate.py --pipeline /path/to/plate-recognition-submit/pipeline.py
```

第二次命令会重新计时。本报告的数字固定为已经写入 `eval/results/` 的那一次，不随以后重跑改写。提交仓库需要 NumPy 2.3.5、`opencv-contrib-python==5.0.0.93` 和 Pillow 12.0.0。本仓库根目录没有 `pipeline.py`；不带 `--pipeline` 时，评测脚本会说明流水线缺失并退出，不会编造识别率。
